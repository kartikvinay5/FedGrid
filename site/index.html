01Introduction & related work

Three properties no single pipeline had combined

Grid operators schedule generation, plan maintenance, and ride out demand spikes on short-term load forecasts. The data that would train the best models is split across state utilities and load dispatch centres that do not pool raw consumption records.

Federated learning removes the need to centralize data by exchanging only model updates. But most federated load forecasting treats each client as independent and ignores a well-established fact: load in one region correlates with load in electrically or geographically adjacent regions. Where federated models do add that spatial structure through graph neural networks, they rarely explain individual forecasts, which limits how far an operator can trust them.

i · Federated

Raw data stays in the state

Only model parameters leave a state. Demand records never do.

ii · Graph-aware

Neighbours inform the forecast

The model sees recent load in bordering states.

iii · Explainable

Every forecast has reasons

Each prediction carries a feature attribution an operator can act on.

03Problem statement

Forecast every state without pooling their data

Given grid zones Z = {z₁, …, zₙ} connected by an adjacency graph G = (Z, E), where each zone holds a private time series of load, weather, and calendar features,

learn a spatio-temporal forecasting model fθ across all zones, with no zone sharing raw consumption records, such that:

(a) Accuracy

fθ beats an equivalent federated model with no graph structure, especially in peak-demand hours.

(b) Attribution

Every forecast returns the input features and neighbouring zones that most influenced it.

04Data

Hourly demand from India's grid operator

Each client is one Southern Region state. The load series is hourly demand met published by Grid-India and downloaded from NITI Aayog's India Climate & Energy Dashboard. The graph links states that share a land border: Telangana–Andhra Pradesh, Telangana–Karnataka, Andhra Pradesh–Karnataka, Andhra Pradesh–Tamil Nadu, Karnataka–Tamil Nadu, Karnataka–Kerala, Tamil Nadu–Kerala and Tamil Nadu–Puducherry.

Jan 2023 – Mar 2026. Values are hourly demand met, not unconstrained demand.

The source repeats some blocks of data exactly: April 2024 is a copy of March 2024 in every state, and March 2026 is a copy of January 2026. Any day whose 24 hourly values match an earlier day was removed, 413 days in total. Weather is hourly temperature from Open-Meteo's historical archive at each state's main load centre (Hyderabad, Vijayawada, Bengaluru, Chennai, Kochi, Puducherry). Holidays come from each state's public-holiday calendar.

05Method

A three-layer pipeline

data_prep.py

Data layer

  • Merges the ICED exports per state
  • Removes copied days
  • Adds state holidays and hourly temperature
train.py

Model layer

  • Linear clients (SGDRegressor); each state scales its own load
  • One-hop neighbour feature from bordering states
  • Sample-weighted FedAvg, 40 rounds × 5 epochs, then 5 local fine-tuning epochs
explain.py

Explanation layer

  • SHAP LinearExplainer
  • Attributions in MW for each forecast, including the neighbour feature

06Results

Personalisation matters more than the graph feature

One shared model has to fit states as different as Tamil Nadu and Puducherry. Letting each state fine-tune the federated model on its own data closes most of that gap. The neighbour feature then adds a small gain, mostly in peak hours.

RMSE by model, MW

ModelMAE (MW)RMSE (MW)MAPE (%)Peak MAE (MW)

Table 1. All six states pooled, 2025 test year, mean ± standard deviation over 5 seeds. Lower is better.

1

Plain FedAvg underfits. A single global linear model is worse than training each state alone, because the states' load patterns differ. Pooling all data into one centralized model has the same problem, so it is not an upper bound here.

2

Personalised federation works. Five local fine-tuning epochs cut RMSE by about 10% against plain FedAvg and match or beat each state training alone, with lower peak-hour error.

3

The neighbour feature helps a little. With personalisation it lowers peak-hour MAE by under 1% and RMSE by about 0.2%. Without personalisation it gives no gain. This is far smaller than the 1.8% the simulated data suggested.

The neighbour feature has the smallest attribution, about MW on average and MW in peak hours. A linear model can only use neighbouring load as a straight-line adjustment, which is one reason the graph attention network remains the main next step.

08Discussion & future work

From linear stand-in to graph attention network

On real data the federated system works once each state can personalise the shared model. The graph feature's benefit is small with a linear model and state-level data. States are large, and their demand is driven mostly by their own daily cycle. The open question for the next stage is whether a graph attention network, or finer zones such as substations, gets more out of neighbouring load.
